- 编写：Claude Opus 5.5 /ybc（Stage0 协调方，仅写文档），2026-09-28。
- 实现与启动：交给执行 Agent（见 [启动提示词](20260928-followup-prompt.md)）。
- 判据预登记：D50（A 线）、D51（B 线），写于实现之前，**实现与运行中不得修改**。
- 目标：执行 Agent 写好代码、验证、一次性启动流水线后即可结束；流水线在服务器上无人值守跑完，并自动生成结论报告。

## 1. 为什么做这两条线

Stage0 的 G0 不通过（见 [stage0 日志](20260928-stage0.md) 的“G0 最终判定表”）：

- R0-3c：失配加强后能显著伤害 SAC（增益 1.8 + 延迟 10 步，成功率 0.70 → 0.33）。
- R0-4b：三种无结构的在线适应（全参数更新、只更新输出层、残差滑动平均）都挽回不到 30% 的失配误差。
- 名义条件（无任何失配）下，约 29% 的回合以 `ik_limit` 失败，即机械臂反复够不到末端参考位姿。

文献调研（[LIT-MISMATCH-028](20260928-lit-mismatch-ik.md)）的相关结论：

- 真实 ROS/Husky 链路延迟一般远低于 100 ms；0.5–1 s 延迟只能算压力测试，不是现实误差。
- 适应机制优先尝试低维的增益、延迟辨识，而不是对 1041 维特征做无结构修正。
- 已有直接近邻工作 MMDirector（用世界模型推演判断移动操作可达性）。因此 B 线必须与**非学习的几何/IK 预检基线**和**历史条件基线**比较，否则无法说明世界模型前瞻的必要性。

两条线要回答的问题：

| 线 | 要回答的问题 |
|---|---|
| A 线（失配 + 结构化适应） | 如果只在线估计 1–2 个物理量（增益、延迟），能否挽回失配带来的预测误差？ |
| B 线（IK 失败前瞻） | 名义条件下的 IK 失败是否可以避免？能否提前预测？世界模型前瞻是否比当前状态、历史、简单几何预检更有信息量？用它做一个简单干预，能否减少失败？ |

## 2. 总体约束

- **所有新行为默认关闭。** `p0_runner.py` 新增的开关关闭时，现有输出（episodes.jsonl 字段、轨迹、观测文件）必须逐字段不变，需做回归验证（§6）。
- **新脚本放在 `src/modulation_rl/scripts/` 顶层，不放进 `scripts/wm/`**，否则会触发 `wm/cache.py:code_identity()`，使已训练的世界模型 checkpoint 校验失败（Stage0 已两次踩坑）。
- 不训练 SAC；不修改奖励、终止、IK、动作语义；评测一律 `--ik-mode fixed --ik-iterations 100`。
- 种子只用下表登记的范围；20000–20299 不得使用。
- 并发：同时运行的 episode-worker 总数 ≤ 64；每批启动前检查可用内存 ≥ 60 GiB，否则等待。swap 当前约有 25 GiB 残留。
- 世界模型：`results/p1-retrain-20260928/trainval-1000-r1/action.pt`（seed11，R0-2 已在独立 test 上验证）。策略与编码器：`results/p1a-20260923/policy-100k.pt`。
- Git：从 `stage0-028` 新建分支 `followup-028`，只按路径提交；不 push、不合并 main、不用 `git stash`。

## 3. A 线：结构化低维适应（离线，不新采数据）

**数据**：R0-4 的 7 个条件（`results/stage0-028-r04/` 下 `gain{0.6,0.8,1.0,1.2,1.4}_delay0`、`gain1.0_delay{1,2}`）与 R0-4b 的 3 个条件（`results/stage0-028-r04b/` 下 `gain1.8_delay0`、`gain1.0_delay5`、`gain1.4_delay5`），每个 100 回合。沿用 `adaptation_probe.py` / `residual_probe.py` 的“先预测后更新、每回合重置、只在未用于更新的后续步上评估”协议和配对统计。特征缓存写到本任务自己的目录，不写进 Stage0 的结果目录。

**变体**（全部无梯度，只估计低维量）：

| 变体 | 做法 |
|---|---|
| V0 冻结 | 对照，与 R0-4b 相同 |
| V4 增益标量 | 用过去步最小二乘估计标量 s = Σ⟨Δ̂,Δ⟩ / Σ⟨Δ̂,Δ̂⟩（Δ̂ = 世界模型预测增量，Δ = 实际增量，只用 robot 块，s 截断到 [0, 3]），预测改为 z + s·Δ̂（只作用于 robot 块）。另报“robot 块和 map 块各一个标量”的版本 |
| V5 延迟选择 | 对候选延迟 d ∈ {0,1,2,3,5,10}，用动作 [a_t[0], a_{t−d}[1], a_{t−d}[2]] 预测（延迟只作用于底盘两维；t−d < 0 时底盘动作取 0，与 mismatch-v1 的初始零缓冲一致）；按过去残差的指数滑动平均（α = 0.2，robot 块）选择 d |
| V6 延迟 + 增益 | 在 V5 选出的 d 上再做 V4 |

**额外报告**：每回合估计的 s 与真实增益的相关性，选出的 d 与真实延迟的一致率（可辨识性检查）。

**判据（D50）**：与 D49 相同。至少一个变体在 {gain1.4_delay0, gain1.8_delay0, gain1.4_delay5, gain1.0_delay5} 中的 ≥2 个条件上，挽回比例 ≥30%，且“变体 − 冻结”的配对 CI 上界 < 0；同时名义条件下“变体 − 冻结”的均值 ≤ 冻结名义残差的 1%。

**解读边界**：即使通过，也只说明低维辨识能改善预测。能看历史的 SAC（S2）也可能自行推断同样的量，这要到 Stage1 才能比较。延迟 5–10 步属于压力档，不代表现实误差。

## 4. B 线：IK 失败前瞻

### B1 可避免性（离线，已有数据）

在 R0-3 与 R0-3c 共 30 个配置、种子 10000–10099（确定性）上：

- 找出名义配置（增益 1.0、延迟 0）中以 `ik_limit` 失败的种子。
- 统计其中有多少在“温和扰动”配置（增益 ∈ [0.8, 1.2]、延迟 ∈ {0,1,2}，共 8 个，不含名义）中至少一次成功 → **失败翻转为成功的比例**。
- 同时统计名义成功的种子在这 8 个配置中至少一次失败的比例 → **成功翻转为失败的比例**，作为“结果本身是否混沌”的对照。
- 另报按任意配置的翻转比例，以及失败回合末段（`episode-*-tail.json`）的 `dist_to_desired` 走势。

**判据（D51-B1）**：失败→成功比例 ≥ 0.30，且高于成功→失败比例（两者之差的 bootstrap 95% CI 下界 > 0）。不通过说明失败主要由场景决定或结果高度随机，B 线前景下降，但 B2/B3 仍照常运行并报告。

### B2 可预测性（新采数据 + 离线分类）

**采数**：种子 1000–1999，确定性策略，名义条件，`--save-observations`，并用新增开关 `--save-step-info` 记录逐步信息。

- `p0_runner.py` 新增 `--save-step-info`：每回合额外写 `episode-XXXXX-stepinfo.npz`，每步字段为 `kin_failure`、`selfcollision`、`base_collision`、`dist_to_desired`、`rot_dist_to_desired`、`nr_kin_failures`。开关关闭时不写任何新文件或新字段。需同时转发到 `episode_command()` 与 `doc/agent_logs/20260928-stage0-shard-eval.py`。

**标签**：第 t 步动作执行后是否 IK 失败，记为 fail[t]。决策时刻 t 的标签 y_t^H 表示 fail[t .. t+H−1] 中是否出现失败，主 H = 5，次 H = 10。只在 fail[t−1] = 0 的步上评估，即预测“新失败的开始”，而不是已持续的失败。

**特征**：编码器、归一化器与世界模型同 §2。z_t 为标准化后的 1041 维特征，a_t 为本步动作，K = 5。

| 分类器 | 输入 | 作用 |
|---|---|---|
| C-geo 几何/IK 预检（非学习基线） | 上一步的 `dist_to_desired`、`rot_dist_to_desired`，末端参考位姿相对底盘的距离（由 robot_state 中的相对位姿计算）；逻辑回归 | 回应 MMDirector 与“简单预检就够”的质疑 |
| C-cur 当前状态 | [z_t, a_t] | 基础对照 |
| C-hist 历史 | C-cur + 过去 K 步 robot 块相对 z_t 的差、过去 K 步动作、过去 K 步 map 块差的范数 | 对应 Stage1 的 S2 质疑，与 C-wm 维度相同 |
| C-wm 世界模型前瞻 | C-cur + 未来 K 步预测的 robot 块相对 z_t 的差、想象动作、map 块差的范数。推演：ẑ_{t+1} = WM(z_t, a_t)；â_{t+j} = 策略对 ẑ_{t+j} 的确定性动作；ẑ_{t+j+1} = WM(ẑ_{t+j}, â_{t+j}) | 被检验对象。**不得使用记录的未来动作**（会泄漏未来信息） |

- 策略动作头：`GaussianPolicy.post_fc_stack → mean_linear → tanh → ×action_scale + action_bias`，作用于逆标准化后的特征。实现后必须用测试证明它与 `policy.predict(map, robot, eval=True)` 在真实观测上一致。
- 离线特征与 B3 在线计算的特征必须来自**同一个模块**，保证训练和部署一致。
- 学习型分类器：MLP 2×256，输入按训练集标准化，BCE 带正样本权重，按验证集 AUROC 早停，3 个初始化种子取平均预测。
- 数据效率曲线：训练回合数 100 / 300 / 700。

**指标**：测试集（1800–1999）步级 AUROC、AUPRC；配对差按测试回合做 bootstrap（10000 次，固定种子）。

**判据（D51-B2）**，H = 5、全量训练集，三项全部满足才算通过：

1. AUROC(C-wm) − AUROC(C-cur) ≥ 0.02 且 95% CI 下界 > 0；
2. AUROC(C-wm) − AUROC(C-hist) 的 CI 下界 > 0；
3. AUROC(C-wm) − AUROC(C-geo) 的 CI 下界 > 0。

H = 10 与数据效率曲线只作次要报告。

### B3 闭环干预（探索性，不作为通过依据）

**`p0_runner.py` 新增 `--shield-config PATH`（默认关闭）**：每步在策略给出动作后，计算风险 r_t = 分类器(特征)。若 r_t > τ，把动作第 0 维（末端参考速度）改为 −1，即最低速度，让底盘有时间跟上；否则动作不变。执行的是修改后的动作。每回合重置历史缓冲。开启时在 episodes.jsonl 行中增加触发次数，在 stepinfo 中增加每步风险与是否触发；关闭时不导入任何新模块、不产生新字段。

**实验臂**（种子 10000–10099，确定性，名义条件，每臂 100 回合）：

| 臂 | 触发规则 |
|---|---|
| none | 不干预（同时与 R0-3c 名义结果核对一致性） |
| wm | C-wm 风险 > τ_wm |
| cur | C-cur 风险 > τ_cur |
| hist | C-hist 风险 > τ_hist |
| geo | C-geo 风险 > τ_geo |
| random | 以固定概率 p 随机触发，p 为 wm 臂在验证集上的触发率，随机数由回合种子派生 |

- 所有 τ 都在 **B2 验证集**上确定，使步级触发率 = 10%（预登记），保证各臂干预预算相同；不得看 B3 结果后调整。
- 报告：成功率、perfect-success、IK 失败回合比例、实际触发率、回合时长，以及各臂相对 none、wm 相对其他臂的配对差与 CI。

**解读**：B3 只是在不训练 SAC 的前提下，用最简单的干预看前瞻信号在闭环中是否可用。结果为负不否定“把前瞻信号接入 SAC”的做法；结果为正也只是探索性证据，正式结论要到 Stage1/2 在未曝光种子上检验。

## 5. 流水线结构（执行 Agent 实现）

- **入口**：宿主上的启动脚本 `doc/agent_logs/20260928-followup-launch.sh`，用 `nohup` 在 `mmhusky-node01` 容器内运行编排脚本 `src/modulation_rl/scripts/followup_pipeline.py`。编排脚本启动前自检 analytical 仿真是否在容器内运行，未运行则自行启动并等待 MoveGroup 就绪。
- **输出根目录**：`results/followup-028/`，下设 `a-structured/`、`b1-avoidability/`、`b2-collect/`、`b2-foresight/`、`b3-shield/<arm>/`、`logs/`。
- **阶段与依赖**：

| 阶段 | 内容 | 依赖 | 并行 |
|---|---|---|---|
| S0 预检 | GPU、内存、磁盘、analytical、checkpoint SHA、git HEAD 与工作区是否干净（记入 manifest） | — | — |
| S1 | A 线离线探针 | S0 | 与 S2、S3 并行 |
| S2 | B1 可避免性 | S0 | 与 S1、S3 并行 |
| S3 | B2 采数（1000 回合） | S0 | ≤ 64 worker |
| S4 | B2 特征、标签、分类器、τ、分类器包 | S3 | — |
| S5 | B3 六个实验臂 | S4 | 各臂串行或少量并行，总 worker ≤ 64 |
| S6 | 汇总报告 | 全部（失败阶段如实标注） | — |

- **可恢复**：每阶段完成写 `DONE` 标记与 `result.json`；重新启动时跳过已完成阶段。某阶段失败时写 `FAILED` 与错误信息，不依赖它的阶段继续运行。
- **状态**：`results/followup-028/status.json` 实时记录各阶段状态、开始/结束时间、当前 worker 数、可用内存。
- **资源守护**：可用内存低于 40 GiB 时暂停启动新 worker；单阶段设超时（采数 3 h、B3 每臂 1 h、离线阶段 2 h）。
- **自动报告**：S6 生成 `doc/agent_logs/20260928-followup-report.md`，包含 D50/D51 各判据的通过表（数值、CI、是否通过）、B3 各臂结果表、所有产物路径，以及一段不超过 10 行的结论。报告只陈述结果，不自行建议改判据。
- **停止方式**：`sg docker -c "docker exec mmhusky-node01 pkill -f followup_pipeline.py"`，再按 `results/followup-028/` 路径 `pkill -f` 残留 worker。写进启动脚本注释与任务日志。

## 6. 执行 Agent 在启动前必须完成的验证

1. **默认关闭回归**：在 10000–10019 上，不带新开关运行 `p0_runner` 评测，与改动前的代码（`stage0-028` 分支 HEAD）逐字段比较 episodes.jsonl 与轨迹文件，必须全部一致。
2. **单元测试**：策略动作头与 `policy.predict` 一致；标签构造（含回合边界、fail[t−1] 过滤）；C-hist 与 C-wm 维度相同；V4/V5 在人工构造的“已知增益/延迟”数据上能恢复真值；B1 翻转统计。现有测试全部通过。
3. **小规模冒烟**：整条流水线缩小规模跑通一遍（例如 B2 采 12 回合、B3 每臂 4 回合、A 线 2 个条件），输出到单独目录，确认报告能生成。冒烟产物不计入正式结果。
4. **提交代码**：按路径提交到 `followup-028` 分支，记录提交号；再启动正式流水线，使 manifest 记录干净的 HEAD。
5. **启动后**：确认各阶段进入运行，在任务日志写明启动命令、PID、日志路径、监控与停止方式，然后结束会话，**不需要守着**。
